## Existing implementation and database

- [pom.xml](../pom.xml) defines Spring Boot 4.1.1 targeting Java 21, with Maven Wrapper, Spring MVC, Jakarta Validation, Spring Data JPA, the SQL Server driver, Spring Security with resource-server JWT, and Boot test starters. `GET /api/hello` is a public starter endpoint, not a chess feature.
- F01 (register/sign in) is implemented in the `account` and `rating` packages: `POST /api/accounts/signup`, `POST /api/accounts/signin`, and authenticated `GET /api/accounts/me`. Errors use RFC 9457 Problem Details with an `errorCode` property via `AppException`/`AppErrorMessage`/`GlobalExceptionHandler`.
- F03 (play against CPU) is implemented in `cpugame` on top of the shared `chess` package: guest-accessible `POST /api/cpu-games` (start; `playerColor` WHITE, BLACK or RANDOM, CPU opens when the player is Black) and `POST /api/cpu-games/cpu-move` (stateless: client sends difficulty, player color and the full UCI move list; the server replays and validates it, then returns the CPU reply, FEN, ply, status and result). Nothing is persisted and no Elo applies; game state stays in the browser.
- F02 (local hot-seat chess) is implemented in `localgame`. Per BR-MOVE-001 the backend validates moves and outcomes; per BR-GAME-004/005 the game state stays in the browser and nothing is persisted. Guest-accessible `POST /api/local-games` validates clock settings (enabled 5–120 minutes and 0–60 seconds increment, or disabled with no timing; omitted fields default to 30+10) and returns the effective clock plus the initial position. `POST /api/local-games/state` is stateless: the client sends the full UCI move list, and the server replays and validates it, then returns FEN, side to move, ply, last SAN move, status, result and the sorted UCI legal moves (empty once the game is over). The clock itself runs in the browser; whether it runs while the browser is closed is still open and only affects the frontend.
- F04 (create and claim invitation) is implemented in `invitation` on top of `onlinegame`. Authenticated `POST /api/invitations` (host picks `hostColor` WHITE, BLACK or RANDOM; clock as in F02, default 30+10) returns a one-time token (32 random bytes, base64url; only its SHA-256 is stored) and expires 15 minutes later. `POST /api/invitations/claim` locks the invitation row (`UPDLOCK`) and atomically creates one PENDING `OnlineGame` (colors fixed at claim, RANDOM resolved then; ready deadline = claim + 3 minutes; rated only with the enabled 30+10 clock); a retry by the same joiner returns the same game. Errors: unknown token 404, expired/cancelled 410, full or own invitation 409. The host polls `GET /api/invitations/{id}` (host-only; status OPEN/CLAIMED/EXPIRED/CANCELLED and `gameId`) and `POST /api/invitations/{id}/cancel` cancels an open invitation; `GET /api/online-games/{id}` is participant-only. Expiry is derived from `expires_at` (expired at or after it); no worker. Real-time claim notification is deferred.
- F07 (ready and start online game) is implemented in `onlinegame`. Participant-only `POST /api/online-games/{id}/ready`, `/cancel` and `/heartbeat` lock the game row (`UPDLOCK`) and return the game. The second Ready before the deadline starts the game once (`ACTIVE`, `started_at` and `turn_started_at` = now); Ready is idempotent. A pending game is cancelled (`CANCELLED`, `ended_at`, `PRE_START_CANCEL`, no result) by an explicit Cancel, by reaching `ready_deadline_at` (claim + 3 minutes; Ready exactly at the deadline cancels), or when a participant has been silent for `app.online-game.pending-heartbeat-timeout` (default 30 s, env `PENDING_HEARTBEAT_TIMEOUT`); claim time counts as first seen and any Ready/heartbeat refreshes the caller. These checks run inside every action and in `PendingGameSweeper` (every `app.online-game.sweep-interval`, default 5 s; disabled in tests via `app.online-game.sweep-enabled=false`). Ready/heartbeat on a non-pending game return its state unchanged; Cancel after start returns 409 `ONLINE_GAME_ALREADY_STARTED` (leaving after start is F11). The response adds `endedAt` and `terminationReason`. Real-time push is deferred; clients poll via heartbeat.
- Product decision recorded 2026-10-15 for F07: pre-start connection loss is a configurable heartbeat timeout of 30 seconds (clients ping about every 10 seconds).
- F08 (make online move) is implemented in `onlinegame`. Participant-only `POST /api/online-games/{id}/moves` takes `{ply, move}` (`ply` = the game's `lastPly + 1`, `move` in UCI) and locks the game row (`UPDLOCK`). A move is accepted only while the game is `ACTIVE`, at the next ply, by the side to move, before the mover's clock reaches zero, and when the chess library finds it legal; it then inserts one `GameMove` row (UCI, SAN, resulting FEN, both clocks, `accepted_at`) and updates `current_fen`, `last_ply`, the mover's remaining time (elapsed time since `turn_started_at` deducted, increment added) and `turn_started_at` in the same transaction. The `GameMove` primary key (`game_id`, `ply`) backs the at-most-once rule. Resending the move already accepted at that ply by the same player returns the current game (200); any other stale or skipped ply returns 409 `MOVE_OUT_OF_SEQUENCE`. Other errors: pending/finished game 409 `ONLINE_GAME_NOT_ACTIVE`, wrong side 409 `NOT_YOUR_TURN`, flag fallen 409 `TIME_EXPIRED` (the TIMEOUT result is recorded separately, see F09), illegal move 400 `ILLEGAL_MOVE`; a rejected move changes no rows. A move that ends the game per the library sets `COMPLETED`, `ended_at`, `outcome` and the termination reason (`CHECKMATE`, `STALEMATE`, `INSUFFICIENT_MATERIAL`, `REPETITION`, `MOVE_COUNT`). `GET /api/online-games/{id}/moves` returns the moves in ply order for refresh; the game response adds `outcome` and `turnStartedAt`. Rated games completed this way are rated by F12. Real-time push is still deferred; the opponent learns of a move by polling.
- F09 (apply clocks and chess outcomes) completes F08's engine-detected endings with timeouts, in `onlinegame`. Clocks are server-authoritative: the side to move is the one whose clock runs from `turn_started_at`, and its flag falls once its remaining time minus the elapsed time reaches zero (exactly zero counts). A move after flag fall is still rejected with 409 `TIME_EXPIRED` and changes no rows; the TIMEOUT result is recorded separately under the game row lock by `ActiveGameSweeper` (same `app.online-game.sweep-interval`/`sweep-enabled` as `PendingGameSweeper`, so it also catches up after a restart) and by a participant's `POST /api/online-games/{id}/heartbeat` on an active game, which returns the completed game. The flagged player loses (`COMPLETED`, opponent `WHITE_WIN`/`BLACK_WIN`, `TIMEOUT`), their remaining time is set to 0, and `ended_at` is the flag-fall instant (`turn_started_at` + their remaining time), not the detection time. A game is completed once: whichever of a move, a sweep or a heartbeat locks the row first wins, and the others see a non-active game. Games without a clock never time out. `GET /api/online-games/{id}` stays read-only and may show `ACTIVE` until the next sweep or heartbeat. Rated timeouts are rated by F12.
- F10 (resign or mutually abandon) is implemented in `onlinegame`. Participant-only `POST /api/online-games/{id}/resign` and `POST /api/online-games/{id}/abandon` lock the game row (`UPDLOCK`) and act only on an `ACTIVE` game (pending, cancelled or completed: 409 `ONLINE_GAME_NOT_ACTIVE`). Resigning completes the game as the caller's loss (`COMPLETED`, opponent `WHITE_WIN`/`BLACK_WIN`, `RESIGNATION`, `ended_at` = now), on either player's turn. A vote inserts one `GameAbandonVote` row (primary key `game_id`, `account_id`; `voted_at`) and leaves the game active and playable; the other participant's vote completes it as `DRAW`/`MUTUAL_ABANDONMENT` in the same transaction. Simultaneous votes or resignations are serialized by the row lock, so the game is completed once. Retries are idempotent: a repeated vote, or a resignation after the caller already resigned, returns the current game (200). If the side to move's flag has already fallen, either action records the TIMEOUT result (as a heartbeat would) and returns it instead. Game responses add `white.abandonVoted`/`black.abandonVoted` so the opponent sees a pending proposal by polling. Rated resignations and abandonment draws are rated by F12.
- F11 (reconnect or forfeit) is implemented in `onlinegame`. Every participant action on an `ACTIVE` game (heartbeat, accepted move, abandonment vote) records the caller's `last_seen_at` and clears their `disconnected_at`; a participant silent for `app.online-game.active-heartbeat-timeout` (default 30 s, env `ACTIVE_HEARTBEAT_TIMEOUT`; exactly the timeout counts) is marked disconnected with `disconnected_at` = their last contact, shown as `white.disconnectedAt`/`black.disconnectedAt`. A participant forfeits once three minutes have passed since their last contact (`DISCONNECT`, opponent `WHITE_WIN`/`BLACK_WIN`, `ended_at` = last contact + 3 minutes), also in invite games without a clock. Clock flag fall (F09) and each player's grace expiry are candidate endings and the earliest instant decides the game; on an exact tie the flag falls first, then the side to move forfeits. Endings are recorded under the game row lock by the heartbeat, resign or vote that finds them due, and by `ActiveGameSweeper` (renamed from `ClockTimeoutSweeper`; same interval and switch), so the game completes once; the running clock is stopped at the ending instant. A move arriving after a forfeit fell due is rejected with 409 `DISCONNECT_FORFEIT_DUE` and changes no rows, like a move after flag fall. `GET /api/online-games/{id}` stays read-only. Pending games keep the F07 heartbeat policy. No explicit leave endpoint exists; closing the tab is detected by heartbeat silence. Rated disconnect forfeits are rated by F12.
- F12 (apply Elo ratings) is implemented in `rating` and hooked into `onlinegame`. Every completion path (move, resign, abandonment draw, timeout, disconnect forfeit; heartbeat or `ActiveGameSweeper`) goes through one completion step under the game row lock, which for a rated game calls `RatingService.applyGameResult` in the same transaction, so the result and both rating applications commit or roll back together. It locks both `PlayerRating` rows (`UPDLOCK`, ascending account id, so overlapping games of one player serialize without deadlock), reads K from `RatingMode.k_factor` (20 for CLASSICAL), updates both ratings, increments `games_played`, and inserts two `RatingEvent` rows (before, delta, after, mode, game, `k_factor_used`, `applied_at`). The `RatingEvent` key (`game_id`, `account_id`) and an existing-events check make it exactly once; a game completes only once, so retries apply nothing further. Unrated games and pre-start cancellations create no events. Ratings are not exposed in game responses; current ratings appear in `GET /api/accounts/me`, and per-game rating history belongs to F13.
- F13 (view match history) is implemented in `onlinegame` by the read-only `MatchHistoryService` (class-level `@Transactional(readOnly = true)`). Authenticated `GET /api/match-history` returns the caller's `COMPLETED` online games only (unrated invites and resignation, timeout, disconnect and abandonment endings included; pending, pre-start cancelled and active games excluded), newest `ended_at` first with `game_id` as tie-breaker (client `sort` is ignored), paged with `page`/`size` (default 20, larger sizes clamped to 100 via `spring.data.web.pageable.*`) in the `common/dto/PageResponse` envelope `{content, page, size, totalElements, totalPages, last}`. Each entry carries the stored effective settings (source, rated, mode, variant, clock), `viewerColor`, the opponent's id and current display name (BR-HIST-005), the perspective `result` (`WIN`/`LOSS`/`DRAW`) next to the stored `outcome` and `terminationReason`, `startedAt`, `endedAt`, `plyCount`, and the caller's own `ratingChange` (before, delta, after, K) or null for unrated games. `GET /api/match-history/{gameId}` adds both players with current names, both players' stored rating changes, initial and final FEN, and the moves in ply order; a non-participant gets 404 `ONLINE_GAME_NOT_FOUND` and a participant asking for a game that is not completed gets 404 `GAME_NOT_IN_HISTORY`. The list query uses the existing `IX_Game_white_history`/`IX_Game_black_history` indexes; rating events come through `RatingService.getGameEvents` (one query per page). Replay UI and a resume view for active games are not part of F13; active games stay reachable through `GET /api/online-games/{id}`.
- Product decisions recorded 2026-10-19 for F13: match history lists completed games only (active games are not listed; a separate resume view is deferred); the list uses the `PageResponse` envelope without a success/data wrapper; the detail shows both players' rating events, and each list entry shows the viewer's own.
- Product decisions recorded 2026-10-19 for F12: simple Elo with expected score `1 / (1 + 10^((opponent - own) / 400))`; the winner's change `K * (1 - expected)` is rounded half up and the loser receives its negative; every draw is +0 for both; ratings never go below 0 (the loser's stored delta shrinks so they stop at 0, while the winner keeps the full change); `games_played` increases by one for both players on every rated game, draws included.
- Product decisions recorded 2026-10-19 for F11: when both players are disconnected, each grace runs independently and the earlier expiry loses; when a clock timeout and a grace expiry both apply, the earliest instant wins; reaching the grace deadline forfeits (a reconnect must arrive strictly before it); disconnection is detected by heartbeat silence (configurable, default 30 s) and the three-minute grace runs from the last contact.
- Product decision recorded 2026-10-19 for F10: an abandonment vote is permanent — it cannot be withdrawn and does not expire, and stands until the game ends.
- Product decision recorded 2026-10-15 for F09: running out of time is always a loss, even when the opponent has insufficient mating material (no FIDE-style draw; the schema allows `TIMEOUT` only with a win and the chess library has no per-side mating-material check).
- Product decisions recorded 2026-10-15 for F08: online games end automatically on the same library-detected outcomes as CPU games (checkmate, stalemate, insufficient material, threefold repetition, 50-move rule; no draw claims); a move arriving after the mover's clock has run out is rejected and F09 records the timeout.
- Product decisions recorded 2026-10-08 for F04: the host chooses their color when creating the link (stored in the new `Invitation.host_color`); the host learns of a claim by polling for now; invitation expiry is derived, not materialized.
- Chess rules come from the imported `io.github.wolfraam:chessgame` library (MIT, Maven Central); legality is checked with its `isLegalMove` before every move because its `playMove(UCI, …)` does not validate. CPU moves come from the official Stockfish binary (GPL-3, run as a separate UCI process, never linked or modified) via `app.engine.stockfish-path`/`STOCKFISH_PATH`; without it CPU endpoints return 503 `ENGINE_UNAVAILABLE`. Do not hand-write chess rules or search.
- Product decisions recorded 2026-10-08 (answering backlog open questions): CPU moves are computed on the backend; Easy/Medium/Hard = Stockfish Skill Level 1/8/15 with 100 ms/300 ms/1 s think time; the player chooses CPU-game color (or random); threefold repetition and the 50-move rule end CPU games as automatic draws (library behaviour). Online games use the same draw policy (decided 2026-10-15, see F08).
- The schema source is the existing `ChessDB` database on the developer's SQL Server; its baseline DDL is not tracked in this repository. Changes on top of it are tracked as idempotent scripts in [db/migrations](../db/README.md) and must be applied to both `ChessDB` and `ChessDB_Test` (001 adds `Invitation.host_color`). Entities map only the tables implemented features need (`Account`, `AccountRole`, `RatingMode`, `PlayerRating`, `Invitation`, `OnlineGame`, `GameMove`, `GameAbandonVote`, `RatingEvent`; `OnlineGame` maps `termination_reason`, `turn_started_at` and the last-seen columns since F07 and `outcome` since F08, and the disconnect columns since F11, but not `version` yet), with explicit table/column names and `ddl-auto=validate`. `Instant` maps to the schema's UTC `datetime2(3)` columns via `hibernate.type.preferred_instant_jdbc_type=TIMESTAMP`. Schema changes still require their own task and a tracked script.
- [application.properties](../src/main/resources/application.properties) reads `CHESS_DB_URL`, `CHESS_DB_USERNAME`, `CHESS_DB_PASSWORD`, and `JWT_SECRET` (base64, ≥256 bits) from the environment; the app fails fast without them. Test configuration starts without a database; SQL Server integration tests run against `ChessDB_Test` only when `CHESS_TEST_DB_*` variables are set.
- Follow chess requirements for stable identity, historical facts, atomic transitions, and idempotency. Invite claims, matchmaking, moves, finalization, ratings, and puzzle-completion imports require the applicable concurrency guarantees.
- CPU/local games and guest puzzle progress remain in browser storage as specified. Do not add server persistence based on marketplace requirements.
- Keep credentials out of tracked files. No `scripts/dev.ps1` or `.local/database.json` loader is present.

## Topic template application and exceptions

The eight topic files retain the source repository's Java/Spring conventions. Apply these project-specific clarifications:

- MapStruct remains the inherited mapping convention. Static mapper sections and calls in examples are reference alternatives, not an instruction to mix approaches. Annotation processing is configured. When mappings are needed, use injected mapper instances for DTO/model and model/entity boundaries. MapStruct annotations and generated Spring integration are allowed by the mapper import rule. Lombok uses the Spring Boot-managed version; MapStruct is pinned to 1.6.3 and lombok-mapstruct-binding to 0.2.0. Apply annotations selectively; existing record DTOs do not need Lombok, and do not retrofit generated entities incidentally.
- For Lombok `@Builder(setterPrefix = "with")` targets, explicit builder mappings may be needed. `Mappers.getMapper(...)` is suitable only for standalone mappers without injected collaborators; otherwise use Spring or explicitly wired collaborators.
- Incoming mappings must exclude server-controlled identifiers, participant assignments, authoritative clocks, ratings, outcomes, and historical fields as required by each operation. Follow the backlog's server UTC requirements for deadlines and clocks.
- The controller checklist asks for a response local although its example returns a mapper call. Use `var response = taskMapper.toDto(created);` followed by `return response;` when mapping exists. The starter hello response needs no business service or mapper.
- Spotless with Palantir formatting is bound to Maven's `validate` phase. `clean verify` checks formatting and runs the tests, including selected ArchUnit package-boundary checks. GitHub Actions runs this command on pushes and pull requests. Local hooks are not installed. Remote required-check/branch-protection settings need administrator configuration; see [shared skills](agent-skills.md).
- The OpenAPI document is generated code-first by springdoc (`/v3/api-docs`, Swagger UI at `/swagger-ui.html`) and documents bearer-JWT auth via `config/OpenApiConfig`; no hand-written contract is established. Paged endpoints return `common/dto/PageResponse` (`{content, page, size, totalElements, totalPages, last}`, no success/data wrapper; decided 2026-10-19 for F13), which resolves the list-envelope reference in [controllers.md](controllers.md). `AppException`, `AppErrorMessage`, and `GlobalExceptionHandler` exist under `common/exception`; add new failure modes as enum values. Preserve the hello response unless a task changes it. Default success codes do not replace appropriate error responses.
- The [startup and endpoint test](../src/test/java/com/swd392/backend/Swd392BackendApplicationTests.java) uses MockMvc with a Spring context. The [processor integration test](../src/test/java/com/swd392/backend/tooling/AnnotationProcessingTest.java) verifies Lombok builders/getters, MapStruct round-trip mapping, and Spring bean registration without a database. No database mapping tests are present.
- Never log passwords, tokens, connection secrets, or complete personal-data-bearing requests. BR-ACC-024 does not require a detailed administrative audit trail at launch; marketplace audit rules do not override it.
- Follow each chess feature's testing requirements, including SQL Server transaction/concurrency tests where specified. Mock-only tests do not establish database integrity.

Raise remaining conflicts between these clarifications and topic guidance with the user. No mandatory commit workflow, delegation requirement, or additional approval gate is adopted by copying these files.

## Build and validation (PowerShell)

Use JDK 21 or newer with `JAVA_HOME` set and the Maven Wrapper.

| Command | Purpose and limits |
| --- | --- |
| `.\mvnw.cmd clean verify` | Check formatting, compile, run architecture/current tests, and package the JAR. Verifies startup, hello, and Lombok/MapStruct processor integration. |
| `.\mvnw.cmd spotless:apply` | Apply Palantir Java formatting to source and test files. |
| `.\mvnw.cmd test` | Run current tests; does not verify unimplemented chess behavior or database mappings. |
| `.\mvnw.cmd spring-boot:run` | Start the application, normally on port 8080. |
| `java -jar target/swd392-backend-0.0.1-SNAPSHOT.jar` | Run the packaged application after building. |

Run checks appropriate to the change. Report actual commands, outcomes, skipped tests, and unavailable checks with reasons. Never present an unrun check or successful starter build as proof of database or chess-feature correctness. Documentation-only imports require file/link validation, not database access or unrelated tooling installation.
